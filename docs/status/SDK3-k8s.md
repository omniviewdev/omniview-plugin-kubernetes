## 3. The unknown count: what it means, why it is an interim, and what the SDK should answer instead

**What the plugin returns, exactly.** When a count cannot be had within 5 s (`replayCountBound`), `ReplayCount` returns `math.MaxInt64` (`replayUnknown`). It means: **the count could not be had within 5 s: this opening is never marked caught up; a consumer must treat a source that is not yet marked as UNKNOWN and must not use the per-line flag of an unmarked source as a fact.** The stream opens at once, exactly as it would without asking, and every line of that opening is flagged `replay`, live ones too; the next opening of the source (a reconnect, a source enabled again) counts again. No number is guessed: not 0 (it marks the source caught up before its replay) and not the lines counted so far (it marks it early). It is stated in the code comment of `replayUnknown`, in the README paragraph and in the PR body, and held by `TestACountThatIsNotHadInTimeLeavesTheSourceUnmarkedAndTheStreamOpen` (a session under the SDK's real manager: the count times out, the stream opens, one count request and one stream request, no caught-up event, every line flagged, the live one too) and `TestReplayCountThatTakesLongerThanItsBoundIsUnknown`.

**Why not an error** (the lead's decision): an error fails the attempt as a failed open does, and the SDK retries the open five times (1 s, doubling to 30 s), each retry counting again up to the bound again, and ends in `STREAM_ERROR`: the logs of a container whose tail is merely slow to count would not open for about a minute and then fail, and the stream is not what failed.

**Why it is a workaround for a missing producer signal.** plugin-sdk v0.22.0 has no way for `ReplayCount` to say "the end of this replay is not known": a count is a number of lines or an error (read in `opts.go`, `manager.go countReplay` and the README of v0.22.0). The SDK does document the state of a source that asked and is not caught up, unknown, and names a count the stream never reaches as the likeliest mistake of a count; the plugin chooses that mistake, here and only here.

**The SDK follow-up, specified for dispatch (the plugin switches when it is tagged).**

- **Name:** `logs.ErrReplayUnknown`, an exported sentinel error. `ReplayCount` answers `return 0, logs.ErrReplayUnknown` (matched with `errors.Is`, so it may be wrapped) when it cannot say where the replay ends.
- **Behaviour of the manager, for that opening and only that one:** it is not a failed open (no retry, no backoff, no `STREAM_ERROR`); `Handler` is called with the same request; no line of the opening is flagged (`LogLine.Replay` stays false); no `SOURCE_CAUGHT_UP` is sent for it; and before the first line of the opening one event is sent, `StreamEventSourceReplayUnknown` (wire `LOG_STREAM_EVENT_SOURCE_REPLAY_UNKNOWN = 8`, additive, `source_id` set, sent whether or not the session set `IncludeSourceEvents`, as the caught-up event is), once per opening. A reopening counts again and decides again. Any other error, and a negative count, keep today's meaning; a session that did not ask is untouched.
- **What the consumer sees:** for a source of a session that asked, the state is unknown until `SOURCE_CAUGHT_UP` (then live) or `SOURCE_REPLAY_UNKNOWN` (this opening will not be marked: unknown for as long as the opening lasts, with no wait for an event that will not come, no spinner and no timeout); the lines of that opening carry `replay=false` and are **not** to be read as live: the event is what says so; no rate is shown for the source; the next opening decides again. `LogSession.ReplayMarkers` is unchanged (the caught-up event can still come for other openings).
- **Plugin change when it is tagged:** `return replayUnknown, nil` becomes `return 0, logs.ErrReplayUnknown`; `replayUnknown` is deleted; the pinned test changes from "every line flagged, no event" to "no line flagged, one `SOURCE_REPLAY_UNKNOWN` before the first line, no `SOURCE_CAUGHT_UP`"; the host's interim rule (do not use the flag of an unmarked source) goes with it.

## 4. (B) The replay count

**Where.** `Handler.ReplayCount` of `k8s:/pods` (`register.go`), `nativeReplayCount` in `replay.go`. The SDK calls it, for a session that asked and a request with `Follow` true, before each opening and reopening of a source, with the request `Handler` is about to get; it holds the source's slot among the session's twenty and delays `SESSION_READY`; for different sources it runs at the same time (a test pins that).

**What it counts.** The lines at the head of the stream `Handler` opens, not what the container holds:

- The request is the stream's own (`podLogOptions`: container from the source's labels or the target, `previous`, `tailLines`, `sinceTime` or `sinceSeconds`, `limitBytes`, timestamps) with follow off, and **none of the finite read's clamps** (a finite read of the plugin stops at 5,000 lines and 1 MiB; the stream does not: a clamped count would be early). A test compares the two requests parameter by parameter, and runs a tail of 6,000 and a limit of 2 MiB.
- **A window of `sinceSeconds` starts at one instant for both.** The kubelet counts back from the moment it receives each request, so the stream's window started later than the count's by the time the open takes, and the stream delivered fewer old lines than were counted (the next live lines were flagged replay). For an opening that asks, the count now resolves the window once, to an instant floored to the second (the precision of `sinceTime`; the window of an asking opening is therefore up to 1 s longer than asked), and the stream of the same opening uses that instant (`openings`: the SDK gives the count and the handler of an opening the context of the source's run, and the plugin keys the instant by it; a stream that no count preceded, a reader that did not ask, is the request it always was). Held by `TestTheWindowOfSinceSecondsStartsAtTheSameInstantForTheCountAndTheStream` (a fake kubelet clock that moves half a second between the two reads, with the plugin's clock on a second and inside one: the stream delivers the lines counted; the same test was red before) and `TestAStreamOpenedWithoutACountKeepsItsRelativeWindow`.
- A line is what a line feed ends (the SDK's reader splits on line feeds). A CR before it is part of the line (CRLF is one line). A record that has no line feed yet is **not** a line: the kubelet ends a finite read with it and holds it back from a follow of a running container until it is complete.
- **The last record that has no line feed is a line exactly when the stream ends where the body does**, because the SDK's reader then gets what is left: (1) a previous instance (its follow ends at its end; a real kubelet once answered for an instance it no longer had with a 115-byte sentence of this kind); (2) a byte limit that cuts a record that is **whole** in the log (verified on a real kubelet: both `follow=false` and `follow=true` return exactly `limitBytes` bytes and the follow ends, `SDK3-k8s/kubelet-probes-output.txt`). A limit that falls inside a record that is **not** whole (a running container's unfinished last record) is not one: the follow holds that record back, so it neither ends there nor delivers it, and the record becomes a live line when it completes. To tell the two, the count asks the kubelet for `limitBytes` + 32 KiB, applies the limit itself, and reads past it only to the next line feed: a line feed there says the cut record is whole. Held by `TestReplayCountOfATailCutByTheByteLimit` (whole records, cut mid-line, on a line feed, above the tail) and `TestReplayCountOfAByteLimitThatCutsTheRecordAContainerIsStillWriting` (the unfinished record: red before this change, the count was one above the stream).

**Per source, as the SDK defines a source.** A source is a `LogSource` (`<pod>/<container>`, labels pod, container, namespace); the SDK calls the count once for each, with that source's request.

| Source kind | Count | Held by |
|---|---|---|
| A Pod's regular, init and ephemeral containers (`PodSourceBuilder`) | each container's own tail | `TestASessionThatAsksIsToldWhereEachContainersReplayEnds` (init 3, app 300 with a tail of 100, side 5, ephemeral 0) |
| The previous instance (`IncludePrevious`) | the previous instance's lines (the stream ends by itself) | `TestReplayCountOfThePreviousInstance`; no previous instance is an error |
| Several containers | one count and one event each, never mixed | the session tests; real kubelet (`twoc`, two containers): a and b flagged 1000 and 1000 for a tail of 1000, one event each |
| A workload's Pods (Deployment, StatefulSet, DaemonSet, ReplicaSet, Job, CronJob: the plugin's resolvers fan out) | each resolved source through the Pod handler (the SDK streams a group's sources through the handler with the smallest key, so its `ReplayCount` decides, and a session of a group resource gets `ReplayMarkers`); a Pod that appears later is counted when its source opens | `TestAWorkloadSessionCountsEachSourceItsResolverGives` (a stub resolver, a late source); real kubelet (Deployment `web`, 2 replicas of `app` and `side`): 4 sources, one event each, `app` flagged 1000 / 6199 / 5000 for tails 1000 / none / 5000, `side` 200 |
| A group's `Follow` false read | not counted: the SDK does not call it (the stream's end is the boundary) | the SDK |

**Errors are errors, never 0.** 400 (a container that has not started, no previous instance), 403, 404, 5xx, a transport failure: returned through the existing `safeLogError`, with the class the stream's open gets for the same refusal (`INVALID_REQUEST`, `FORBIDDEN`, `NOT_FOUND`, `PROVIDER_ERROR`, `UNAVAILABLE`; one test compares both) and none of the Kubernetes text (a test carries `secret-denied-text` through the log lines and the span). A source or a caller that gave up (`context.Canceled`) is an error, not unknown. The SDK retries the attempt with its backoff, as for a failed open.

**Memory.** One 32 KiB buffer from a pool per count in progress, whatever the tail, the byte limit or the length of a line: the body is counted as it arrives and dropped (`bytes.Count` of a line feed over each chunk). A session reads at most 20 sources at once, so one session's counts hold at most 640 KiB. Held by `TestCountLinesHoldsNoLineInMemory` (a line of 1 GiB: every read at most 32 KiB) and `TestReplayCountOfAHugeLineAllocatesNothingOfItsSize` (a line of 192 MiB over HTTP: under 8 MiB allocated in total; the negative control reads the body whole and both go red).

**Time.** `replayCountBound` = 5 s for the whole read, from the request to the last byte (a read that never answers and a body that never ends are both tested). Why 5 s: the SDK adds no timer and the opening waits for the count, so it is the longest the count can delay a source's first line; 10 MB over a 16 Mbit/s link is 5 s, and a stream slower than that is slow to deliver the same tail anyway; it is also the bound the plugin's discovery gives an extension group's document, for the same reason. A count not had by then is `replayUnknown` (section 3), logged at Warn (`native log replay not counted within its bound`, with the bound and the time taken), and the stream opens at once.

**Cost, as measured here.** Median of 20 opens per leg, legs interleaved, one plugin process per build, load average 15 to 22 (shared machine), kind v0.30.0 / v1.35.0, the kubelet's `containerLogMaxSize` raised to 100Mi so that the 15 MB log is not rotated away:

| Case | BASE, no ask | HEAD, no ask | HEAD, asking: first line | HEAD, asking: caught-up event | extra to the first line |
|---|---|---|---|---|---|
| `rate5`, tail 1000 (132 KB) | 5.9 ms | 6.2 ms | 22.0 ms | 37.3 ms | **+15.8 ms** |
| `bigtail`, tail 1000 (10 MB) | 15.1 ms | 15.7 ms | 87.8 ms | 160.7 ms | **+72.1 ms** |
| `bigtail`, no tail (the whole 35 MB log) | 8.3 ms | 8.8 ms | 267.9 ms | 571.8 ms | **+259.1 ms** |

Without asking the first line is the same within noise (+0.3, +0.6 and +0.5 ms against BASE). The count read alone (client-go, no plugin): 16.6 ms for 1000 lines, 125 ms for 10 MB, 383 ms for 35 MB; the plugin's own debug line reported 32 ms, 62 ms and 146 ms under load (30 MB). Max/p90 and every raw sample are in `SDK3-k8s/results.md`, section 4. A count over its bound was not seen (the largest took 0.4 s), so that path is held by the tests only. The SDK's review measured +12 ms and 0.1 MB for the default tail of 1,000 lines of 100 bytes and +86 ms and 10 MB for a tail of 10 MB, on loopback; a request with no tail counts the whole current log file (10 MiB with the kubelet's default rotation). One extra request per opened source: the connection's limiter allows 50 a second with a burst of 100 (`kubeauth.ConnectionQPS`), so a workload of 40 containers is not throttled, and its counts are serialised only by the SDK's 20 slots.

**What it does not do.**

- It does not validate the count against the stream (the SDK cannot either). If the log rotates between the count and the open, the SDK's documented effects apply (fewer lines than counted: the next live lines are flagged until the count is reached, and a quiet source stays unknown); the plugin only counts, and a test shows that asking changes no line of the stream (the same lines with and without asking, over a scripted rotation).
- A line of 1 MiB or more breaks the SDK's own line reader (`MaxScannerBuffer`), in the stream, before and after this change (read in `readStream`, not run). The count counts it as a line, as the kubelet delivers it (verified on a real kubelet: a line of 2.5 MB is one line), so such a source does not report caught up before its stream fails.
- **Two limits remain, both inside what the SDK documents (a count is a number, not an identity):** (1) the instant an asking opening's `sinceSeconds` window starts at comes from the plugin host's clock, so a host clock that is off by a few seconds from the cluster's moves the window of an asking opening by that much (the count and the stream agree with each other, which is the point, but not with the cluster's idea of "N seconds ago"); a clock taken from the server (its `Date` header, which needs a hook in the client's transport) would remove it and is a follow-up; (2) a record longer than the 32 KiB read past a byte limit that crosses the cut is taken to be whole (the unfinished record of a running container, which containerd never leaves in a log file, would have to be that long). The real kubelet runs of `since 30 s` (149 flagged, 149 in kubectl's window, with and without a tail) and of byte limits (31 lines at 4000 bytes, the fragment included) agree with the count.
- It does not cache a count (each opening counts again, as the SDK's contract says), and it does not read without timestamps to save bytes (a byte limit counts the timestamps, and the two reads must cut at the same byte).

## 6. The real kubelet

**What the fake kubelet assumes was checked against a real one** (kind v0.30.0, node v1.34.0, my own cluster `sdk3k8s-lead`; `SDK3-k8s/kubelet-probes.sh.txt`, output `kubelet-probes-output.txt`): `limitBytes` cuts both `follow=false` and `follow=true` at exactly the limit, in the middle of a line, and ends the follow; the error texts for a container that has not started, no previous instance and a missing Pod are the ones the fake serves; `previous=true&follow=true` ends by itself; a line of 200,000 or 2,500,000 bytes is one line with one timestamp, and the two reads are byte-identical. Two things that I could not make a kubelet do and the fake covers: a record with no line feed (the runtime holds a partial record in its own buffer until the line ends, so it never reaches the log file while the container is running), and CRLF (the runtime's reader strips the CR before the log is written, so a real log has none).

**The proof, through the real plugin binary:** through the real plugin binary (go-plugin as the host launches it), driven by a client built on SDK v0.22.0 that asks with `params["omniview.log.replay-markers"]="1"` and one that does not (`SDK3-k8s/results.md`, section 3, and `compare.txt`). 70 sessions per build:

- **BASE (SDK v0.20.0) and BUMP (v0.22.0, no count):** all 35 asking sessions got `ReplayMarkers=false`, 0 lines flagged and 0 events: an older plugin only echoes the parameter, the stream is what it was.
- **HEAD:** 35 of 35 asking sessions accepted (`ReplayMarkers=true`); 88,130 lines flagged and 48 caught-up events.
