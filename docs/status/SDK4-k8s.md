## 2. Does the plugin's exec terminal implement `exec.EndMarker`?

**The plugin has no terminal of its own, so there is nothing to add.** Read in `pkg/plugin/exec` and the SDK:

- The plugin registers its handlers with `exec.RegisterPlugin(plugin, exec.PluginOpts{Handlers: ...})` (`register.go`). `PluginOpts` has no terminal option, and the SDK builds the manager with `ManagerConfig{Logger, Settings, Handlers}`: no `TerminalFactory`, so the default, `NewRealTerminalFactory()`, makes every session's terminal. The repository defines no `exec.Terminal` type; its tests use `exectest.Mount`, whose `FakeTerminal` implements `EndMarker` since v0.22.1.
- The SDK's real terminal (`terminal_real_unix.go`, `realTerminal`) implements `EndMarker` (`MarkEnd` writes the mark to the slave). On platforms with no pty the SDK's factory fails every session with `pty.ErrUnsupported`, before and after this change.
- What the plugin does with the terminal's slave, which the manager passes to its handlers (`PodHandler`, `NodeHandler`): `streamPod` hands it to client-go's `remotecommand` as `Stdin`, `Stdout` and `Stderr` of one stream (`Tty: true`) in a goroutine, and when the stream returns sends its error, or nil, on `stopCh`, which is how the SDK learns the process is over. It **never closes the slave** (no `Close()` call in the exec package), so it cannot take away the file the manager writes the end mark to. The stream returns after the remote output has been copied to the slave (the control in section 3 holds that: client-go delivered all 65,536 bytes into memory in 400 of 400 runs), so the mark follows all of the output.

The plugin therefore gets the end mark by being rebuilt on v0.22.1, and nothing else.

## 3. The proof: a command that prints 64 KiB and exits at once

**Surface.** The real plugin binary, launched as the host launches it (go-plugin, the SDK handshake, AutoMTLS, a throwaway HOME), a client built on SDK v0.22.1 that calls the exec RPCs in the host's order (one long-lived `Stream` per plugin; per session `CreateSession` with the pod's canonical reference, route and body, then `AttachSession`, then the frames of the session until its Close signal), a real kind cluster (kind v0.30.0, node `kindest/node:v1.34.0`, containerd 2.1.3, pod `busybox:1.37.0` sleeping), on this Mac (Apple M5 Max, macOS 27.0.1: the pty is macOS's). **BEFORE** = `origin/feature/ui-next` `15cf335` (SDK v0.22.0; binary sha256 `57c04c34b93bb3eb971a292d48d1b4346e1e8270ae86033d5f469984ca75c649`), **AFTER** = this tree (SDK v0.22.1; sha256 `77fbee211f77b881d79b114f199138db8ac524c74f26cfab3608daa4c807ada0`); `go version -m` of each binary shows the pin, and `diff -rq` of the two trees shows `README.md`, `go.mod` and `go.sum` only. Both ran at the same time against the same pod, in alternating blocks.

**The command.** `sh -c 'head -c 65521 /dev/zero | tr "\0" x; printf ENDMARK-0123456'`: exactly 65,536 bytes, no newline (a tty would translate one), and the command exits at once. What a session delivered = the `AttachSession` snapshot plus the `Data` of the frames that carry no signal (the Close signal's own "Session closed" text is not output). Anything but those 65,536 bytes is a loss (fewer) or a leak (more, or other: the SDK's end mark must never reach a consumer). **Two independent full runs** (new plugin processes each): run-1 (an earlier version of the tool, legs M1-M4) and run-2 (the committed tool, through `redo.sh`, legs M1-M5); the machine was shared (load average 12 to 64: each leg's load is in `tables-run-*.md`).

| Leg | BEFORE (v0.22.0) | AFTER (v0.22.1) |
|---|---|---|
| **M1** host-like, attach at once, sequential, 2 x 200 runs | **5 of 400 runs lost bytes** (3 + 2), 1,550 B in all, 1 to 1,024 B each | **0 of 400**, 0 B; 400 exact |
| **M3** eight sessions at once on the one Stream, 2 x 200 runs | **22 of 400 runs** (9 + 13), 3,483 B, 1 to 1,024 B each | **0 of 400**, 0 B; 400 exact |
| **M2** late attach: the first attach 1.5 s after the create, when the session has ended, 2 x 100 runs | first attach **NotFound in 200 of 200**: all 65,536 B lost each time | first attach returned **all 65,536 B, exact, 200 of 200**; the second attach and `CloseSession` of the ended session answer NotFound (200 of 200, both builds) |
| **M5** attach after 0 ... 400 ms (run-2, 20 runs per build and delay) | first attach NotFound: 0/20 at 10 and 20 ms, 1/20 at 30, 10/20 at 40, **20/20 at 60 ms and every longer delay** | 0/20 at every delay; every run exact |
| **M4** control, no plugin: client-go `remotecommand`, Tty, websocket, into memory (400 runs); `kubectl exec` without -t (100 runs) | 0 of 400 lost; 65,536 B in 100 of 100 | same cluster and pod |
| Leaks (extra or other bytes, the end mark) | none | **none** in 800 (M1, M3), 200 (M2) and 200 (M5) runs |

What it says:

- **The tail loss is real and small.** In all 27 lossy runs (`lossy-runs-before.jsonl`) the delivered bytes are an exact prefix of the payload (the tail is what was lost): 14 runs lost 1 to 15 B, 11 runs 257 to 269 B, 2 runs 1,024 B (5,033 B in all). The rate depends on concurrency and load: sequential 5 of 400 (1.25 %), eight sessions at once 22 of 400 (5.5 %). Fisher exact, two-sided: M1 alone p = 0.06 (**not significant by itself**), M3 alone p = 3.5e-7, M1 + M3 pooled 27/800 against 0/800 p = 1.2e-8. AFTER lost nothing in 800 pooled runs (exact 95 % upper bound on its per-run rate 0.37 %).
- **It is not the cluster's or client-go's.** The control (no plugin, same pod, same command) lost 0 bytes in 500 runs, and the SDK says why for the plugin: closing the terminal discards what the reader has not taken (macOS flushes the pty queue when the slave closes), which the end mark now waits for.
- **The bigger loss on v0.22.0 is the attach that comes after the session ended** (M2, M5): this command is over about 40 to 60 ms after the create on this cluster, and every first attach later than that answers NotFound on v0.22.0, so the whole output is gone (65,536 of 65,536 B); v0.22.1 keeps it for the first attach and returns all of it, every time. Through the host that attach still fails today for a reason outside the plugin (section 5).
- **The cost of v0.22.1 is not measurable here.** The Close signal can follow the exit by up to about 500 ms by design (the wait for the end mark); create to Close medians, BEFORE against AFTER: M1 run-1 115.1 against 129.0 ms (load swinging from 28 to 64), M1 run-2 43.0 against 42.0, M3 run-1 69.0 against 67.0, M3 run-2 67.0 against 68.0 ms; the worst Close was 294.6 ms (AFTER) against 314.0 ms (BEFORE) in M1 run-1. The 14 ms gap of M1 run-1 falls in that leg's load swing. [INFERENCE] the mark is read in the same milliseconds as the data, so the wait is paid only when the reader is behind.
- **Checks that could have invalidated it, all clean:** 0 exec errors, 0 timeouts (30 s) on either build; 0 sequence gaps in any session's frames; 0 frames of unknown sessions, 0 data frames after a Close signal, 0 repeated Close signals, 0 sessions left in either plugin at the end (`ListSessions`); the pod's uid and restart count were the same at the start and end of both runs; in M1 and M3 the snapshot was empty in every run (the attach came before the first byte: those legs measure the end-of-session loss, not the attach race).

**Seen red.** The proof is the test of this step: red on v0.22.0 (27 of 800 sessions lost their tail; every attach that came after the end lost everything), green on v0.22.1 (0 of 800; all 200 late attaches of M2 exact). A unit test in the plugin would have to fake the Kubernetes exec endpoint (a websocket protocol server) to run the plugin's real handler, and the SDK holds the behaviour with its own tests on a real pty (`TestTailIsDeliveredBeforeClose` in `legacy_repairs_pty_test.go`: 65 of 200 runs lost bytes on `main` before the change, as its PR #89 says); the plugin's CI is unchanged.

**Not run.** A Linux pty (the SDK says Linux can drop a chunk under load); the host application or its UI (the real attach latency: M5 stands in for it with fixed delays); a consumer slower than the tool's (the tool drains its Stream at once: [INFERENCE] a slower consumer makes the tail loss more likely); other payloads (newlines and ANSI, other sizes, long-lived or interactive sessions, stdin, resize, node exec, attach mode); the retention limits (32 sessions, one minute: one retained session at a time was consumed at once); a `CloseSession` racing the process's own end; the SPDY transport (all 400 control runs used websocket); an idle machine. Run-1 used an earlier version of the tool (no M5, no interrupt stop); run-2 used the committed one (its source differs from the committed file by two doc-comment lines).

## 4. What else v0.22.1 changes for the plugin's consumers (read in the release notes, not run unless stated)

- The Close signal can follow the process's exit by up to about 500 ms (the manager waits for the end mark, bounded): measured in section 3 (create to Close).
- The first attach after a session ends returns its output (at most 32 sessions, one minute); a second attach, and `CloseSession` of a session that has just ended, answer NOT_FOUND. The host's UI flow needs its own change for the first (see "What users see").
- A second `Stream` gets its own channel; the end of a stream ends the sessions it served. The host opens one stream per plugin and keeps it.
- Session ids must be unique for the life of the process: the plugin never makes one (the host sends a UUID).
- No wire change.
