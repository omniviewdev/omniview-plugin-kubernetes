# `ui/src/kinds/`: the kinds the plugin lists

Every kind of Kubernetes object the new UI lists is a **definition** (`definition.ts`, `KindDefinition<TRow>`): its identity, its columns and how each cell reads a row, the mapping of its state words to the kit's seven state roles, its quick filters, its default sort and, when the plugin has one, the page of one object it links to. ONE generic list page (`list.tsx`, `listPage(definition)`) draws any definition and ONE data hook (`useKindRows.ts`) reads any of them; neither knows a kind, and a kind is added by writing its definition and a line in the registry (`index.ts`), never by a branch in them. The shape is the mock's definition record (`k8s-resource-definitions.js`, chapter 17 K60 and K61); the Pods list was written first (the host's `ui-next/k8s/` of decisions A13 and A16, tracker row N19) and was moved here, then made the first definition (step K2a, `docs/ui-next/status/K2a.md` of omniviewdev/omniview).

## The rules

1. **It imports only what a new-UI plugin may:** the runtime's curated entry (`@omniviewdev/runtime/ui/v1`, never its main barrel, which holds the previous UI library), the kit (`@omniviewdev/kit`, never its stylesheet, which the host loads once), React and third-party packages; the tests use `vitest` and `@testing-library/react`. The build holds the same line: `vite/omniview.ts` fails on any other bare import and `scripts/check-bundle.mjs` reads the finished bundle.
2. **It reads only through the fenced hooks** (`useResourceTypes`, `useResolvedResourceTarget`, `useResources`, `useConnectionReadiness`, `useConnections`): no raw RPC, no Wails binding. The providers those hooks read (the QueryClient, the theme, the activity provider) are the host's.
3. **A generic file never branches on a kind** (the plugin's `CLAUDE.md`: composition, never a switch on a resource key). What differs between kinds is data in a definition.

## The sidebar's counts (`ui/src/sidebar/`)

Each entry of a kind in the sidebar draws how many objects the kind has: a number (`1,234`), an approximate one for an estimate (`~1,234`, named "about 1,234") or nothing (the slot is held, empty, so a count that arrives moves no label). The static skeleton (`sidebarNodes()`) declares `count: null` on every entry of a kind, which the host reads at admission (a host that predates the slot refuses a `null` count by name), and the sidebar's hook (`useNodes`, `sidebar/useSidebarNodes.ts`) answers the same nodes with the counts once it knows the connection. A group has no count.

| File | What |
|---|---|
| `count.ts` | `sidebarCount(count)`: what a page says it holds (`sourcePage.count`) as the entry draws it. `exact` is the number, `estimate` is `{ value, approximate: true }`; `unknown`, no count, a value that is not a canonical decimal and one beyond `Number.MAX_SAFE_INTEGER` are `null`: no dash and no zero for a count it does not have. |
| `scope.ts` | The namespaces a count is read in (`all`, or `oneOf` a few): the one constraint on the namespace dimension that goes to `useResolvedResourceTarget` for a namespaced kind (sorted, each once), a key, the words for a sentence, and whether a catalog type is namespaced. There is no namespace menu yet, so the sidebar and the lists read every namespace; the scope is still an input of the count hook, so a change of scope reads again what depends on it. |
| `store.ts` | The scheduler, with no React in it: what is wanted in row order, FOUR slots (the backend's `CountConcurrency`), what each read answered and when. A job is due when it has no answer or the answer is older than `REFRESH_MS` (60 s), and never when its last read was refused (`refuse`: it is forgotten, and so asked once more, when the wish drops the kind and names it again); `settle` frees a slot and the next due job takes it; `want` replaces the wish and drops what is no longer wanted from its slot (cancelling its read); a timer asks again when an answer falls due. The clock is injected. |
| `useSidebarCounts.ts` | The hook that reads: the runtime has no hook that reads a number of kinds and a hook cannot run in a loop, so one `useCountSlot` is called four times, each reading what the store gives it (`useResolvedResourceTarget` for the kind, then `useResources` with `pageSize: 1` and no collection). The catalog and the connection's readiness are read once for the whole sidebar. |
| `openCounts.ts` | A small module-level registry: a list that is open publishes its own count (live, from its own source) under its plugin, connection and type, and takes it back when it goes. |
| `useSidebarNodes.ts` | `useNodes`: the connection the pages read, the counts, and `sidebarNodes(counts)`; the same array until a count changes; nothing (so the skeleton stays) while the connection is not known. |
| `testing.ts` | Test support: a fake of the runtime's hooks that counts the reads it is asked for (a read starts when a request key appears and is dropped, cancelled if it is in flight, when its last observer goes). Nothing else imports it. |

What a count costs is held to what is on screen: only the kinds of the top level (Nodes, Namespaces) and of the groups the host says are open (`SidebarContextV1.open`); only for a connected connection (a read never connects) and for the kinds the catalog serves; never for a kind whose list is open (its row follows the list's own count, with no second request); a count is read again after 60 s and not before, however often the sidebar renders, so the backend's 30 s window and its four count reads at a time are never asked more of; collapsing a group cancels what is in flight for it. A failed read and a cancelled one draw nothing and are asked again at the interval like the rest. A refused read (FORBIDDEN, a 403) draws nothing too and is NOT asked again on a timer: a kind the user may not list is asked once, and again only when its group is opened again, the connection or the namespaces counted change, or its list was open (a visit); a 403 every minute is noise in a cluster's audit log, for exactly the users who get one. The entry stays usable either way.

A list the user may not read is the same refusal on its own page: the page says `You do not have permission to list <Plural> in all namespaces.` (`in this cluster` for a kind that lives in no namespace) in the plugin's own words, never the runtime's, and draws no Retry, because asking again cannot change it.

## The cluster Overview (`ui/src/overview/`)

The page a connection opens on (`home`) and the first entry of the sidebar: the mock's cluster overview (`k8s-cluster.js`) as an `overview` page of the contribution, which the host draws with its detail page (the header with the connection's name and a `Connected` chip, the facts, the page's own Refresh, the one `Overview` tab). It answers three of the mock's five questions from three sections in the main column: **Needs attention** (a list: one row for the objects of a kind that fail in one way, `3 Pods in CrashLoopBackOff`, a row `<Kinds> can't be listed` for a read that failed or was refused, and `N API groups are unavailable`), **Workloads** (a table: the kinds the cluster serves, with Status, Total and Failing) and **Cluster** (the version, the Nodes that are ready, the Namespaces, the API server). The summary line says `Everything is running` only when every read of the kinds that can fail is whole and nothing fails. What is not built, and why: Usage (no metrics hook reaches the UI), Recent warnings (the plugin has no Events kind), the Metrics tab, Disconnect and Connection settings, CPU and Memory capacity and Runtime (no Node row carries them), and links that carry a quick filter (a list has no filter a route can name, so a link goes to the whole list).

A read that fails under an open page leaves the rows of its last good read (the runtime's query keeps the data of a refetch that failed), and the page says they are what was last seen and never what is: the Workloads row keeps its Total and says `Read failed` (or `Access denied`), its Failing is `Not checked`, or `N+` when some were failing; the Nodes and Namespaces rows say `3 · 3 ready · could not be refreshed`; and the summary says `Not checked: <kinds>`, never `Everything is running`.

| File | What |
|---|---|
| `assess.ts` | The mock's `assess` over the kinds' own rows: a rule for each kind (`podRule`, `jobRule`, `nodeRule`, `workloadRule`, `daemonSetRule`, `claimRule`) that reads the row's status word and role and never words a state again, and `observe`: one kind's read as the overview says it (served, how many are here and whether that is all, what failed and why in the lists' words, which objects fail). |
| `facts.ts` | The connection's facts through `useConnectionMetadata` (`kubernetes.server_version`, `server_url`, `provider`, `distribution`, `unavailable_api_groups`): each is current, stale, unavailable, absent or on its way, and a fact that is not current is never drawn as current. |
| `model.ts` | The overview as plain data, a pure function of the observations and the facts: the sections, the summary, the header. Every state of the page is a case of `model.test.ts`. |
| `view.tsx`, `cells.tsx` | The model as the host's `DetailView`, from the kit's atoms. |
| `state.ts` | The state of the page while its connection is not ready: what the Pods list says for the same phase, in the detail page's words (`connectionState`, `connectionSentence`). |
| `useOverviewPage.ts` | The page's one hook. It reads nine kinds through `useKindRows`, written out (a hook cannot run in a loop), and the connection's facts: nine collections, and a first page of 256 for each until its collection has answered (the reads of nine lists, none a list does not make). A page that is not on screen holds none (the host hides it in `Activity`). |
| `useNow.ts` | The instant a claim is judged at, looked at again when a claim that waits will have waited five minutes: nothing in the data changes then. |
| `entry.ts`, `page.ts` | The page's id, tile and sidebar entry, and the page itself (`satisfies OverviewPageV1`). |

## The landing (`ui/src/landing/`)

What the window opens when the plugin is opened and no connection is chosen (Home's row of the plugin, `+`, the palette's row, a sidebar entry or a link that names no connection): the plugin's home page (the mock's `kubernetes/home`) and the page of all its connections (`kubernetes/connections`), two `custom` pages of scope `plugin` that the plugin draws itself from the kit (`landing` in `entry.ts` names the first). They are read in no connection, so the window draws no sidebar and no scope lane for them, and the home page links to the other with the kit's `Link`. A connection that is chosen opens `home`, the cluster Overview, as it always did. The pages read the window's own list of the plugin's connections (`context.connections`: the host's word and role for each state, `open` and `refresh`) and keep no list of their own; the plugin's own list (`useConnections`, which the other pages read the connection by) adds the names that tell two connections of one name apart and the labels the configured facts come from.

**What each connection is offered.** One button, from the state the host says it is in, which always asks the host to open the connection (the host starts it first when it is not connected, and only a connection that is connected is routed to): `Open` for a connection that is connected, stopped or starting (busy while it starts), `Sign in` (the one filled button) for one that needs a sign-in, `Retry` for one that was refused, does not answer or did not start. For a start that failed the line under the name is the host's reason. The `…` menu, and the context menu of a row or a card (one `useMenu` for the page): Open, Open in new tab, Copy name.

**What the facts are.** The Kubernetes version, the platform and the region are read from what the plugin already has, never by connecting: the labels the backend gives a discovered connection (`kubernetes.platform` says where the cluster runs when the kubeconfig says it for sure; `cloud.region` the region; the full list is in `pkg/plugin/resource/connection_labels.go`) are there for every connection, and what the backend publishes about a connection that is connected (`useConnectionMetadata`: `kubernetes.server_version`, `kubernetes.provider`, `aws.region`, `gcp.region`) is read only for one that is. What is not known is the kit's dash with what it is and why (`Connect to see the version.`), and what is on its way is left empty, never a dash or a zero. Not drawn, because the plugin does not have them: the Node count (one read of the cluster for each connection, not a fact the backend publishes), the environment (production, staging) and the platform of a connection that is not connected and is not EKS, GKE or AKS (the backend infers a kind or a minikube from the context name only once it is connected). The mock's Platform and Environment filters, the grouping of the cards by environment, the Columns chooser, pinned and recent connections, folders and saved views, Quick view, Open in a new window, Pin, Edit name, Connect, Check, Disconnect, Connection settings and Remove wait for what the host's seam does not offer yet.

| `facts.ts` | The configured facts (`configFacts`) and the three readers (`versionOf`, `platformOf`, `regionOf`): what a cell says of a fact, from the labels and the connection's metadata. |

| `hooks.ts`, `clipboard.ts` | The plugin's own list, Refresh, the page's one menu, and the copy of a name. |
| `home.tsx`, `list.tsx` | The two pages: the header, the section of the first eight connections and the link to all of them; the data view with the strip, the search, the table or cards and the footer. |
| `entry.ts`, `pages.ts` | The ids, the tile and the words, and the pages themselves (`satisfies CustomPageV1`). |

## Adding a kind

1. A directory `<kind>/` with `object.ts` (what the list reads of the object: each field kept only when it has the type the API gives it), `row.ts` (the row, `rowModel(decode, searchParts)`, the status word from the kind's own mapper and `statusOf`) and `definition.ts` (the `KindDefinition`).
2. If the kind can say a state word the table in `status.ts` lacks, add it there in the role K61.3 gives it.
3. The golden test first: `fixtures/<kind>-table.json` is ONE response of a real API server, the objects and the cells its printer made of them (`hack/kinds-capture/capture.mjs`, `ONLY=<kind>` to capture one; the states the host's slice fixture does not make are in `hack/kinds-capture/extra-states.yaml`, `more-kinds.yaml` and `k2b2-kinds.yaml`, made by `more-kinds.sh` and `k2b2-kinds.sh`; `k2b2-kinds.sh` also installs metrics-server, which is what gives the autoscalers their words). A fixture keeps no Secret value: the capture empties them. The test compares the row with the printed cells, and the state word with the counts in them where kubectl prints no word.
4. A line in `index.ts`: in a group of the sidebar, or at the top level for a kind that lives in no namespace. The sidebar entry, the page and the tab are made from the definition. A kind the kit has no glyph for wears `GENERIC_TILE`; a kind whose mock definition has no `quick` has no quick filters, and so no strip.
5. Optionally, a `detail` part in the definition (the page of one object, below): the kind's `detail.ts` with its `overview` and its `commands`, a golden test against `fixtures/<kind>-detail.json`, and the part in `definition.ts`. A definition without one keeps its rows non-navigating: the name in the list is plain text, and a reference from another object to it is plain text too (`index.test.ts` and `cells.test.tsx` hold both).

`index.test.ts` holds every definition to the facts the generic page and hook rely on.

## A Secret's values never reach the page

The plugin's backend sends no Secret value on any read: a list, a page, a Get, the result of a mutation, the live source, the source narrowed to one object (`pkg/plugin/resource/resourcers/projection.go`). The record of a Secret holds its metadata, its type, whether it is immutable and, for each key of `data`, the key's name and its size in bytes (`data: { <key>: { size } }`); the annotation that `kubectl apply` fills with the manifest (`last-applied-configuration`, which holds `stringData` in the clear) is left out. The record's coverage says so (`partial`, with those paths). `secrets/object.ts` counts the entries of `data` and still never reads one, so what a backend should send by mistake would reach no row. A Reveal of one key is not built: the runtime's curated entry (`ui/v1`) has no operation that asks for one value without caching it, so it waits for one (the host's `docs/ui-next/status/SEC1.md`, Backend catalog).

## The page of one Pod reads through this layer too

`ui/src/pod/` (the detail page) uses this layer's `state.ts` (the same words for the connection and the read), the Pod definition's type and `useKindRows.ts`'s `FIRST_SET`, `PLUGIN_ID` and `settled`. Its read is one file, `ui/src/pod/data/usePod.ts`: the page narrows the read to its Pod by namespace and name (a query dimension of every native kind, D1c), so its source view holds that one object. The generic page below does the same for the kinds that have a `detail` part; the Pod's page is its own (`ui/src/pod/`) and keeps its own copy of the read, the Conditions table and the labels, which the generic ones are held to by parity tests (`detail/metadata.test.ts`, `detail/conditions.test.ts`): moving the Pod page onto them, and deleting the copies, is a later step.

## The page of one object (`detail/`)

A kind's definition has an optional `detail` part, `KindDetail` (`definition.ts`): the id of its page (the Kind in lower case: `deployment`), the route parameters that name an object (`['namespace', 'name']`, or `['name']` for a kind that lives in no namespace: the catalog's own dimensions), `overview(record)` and `commands(record)`. ONE generic page (`detail/page.ts`, `detailPage(definition, resolve)`) draws any kind that has an overview, reads it through ONE data hook (`detail/useKindObject.ts`) and knows no kind; a kind's page is added by writing its `detail.ts` and its line in the definition, never by a branch in them. Its shape is the mock's `overview(record)` (`k8s-resource-definitions.js`: `{ state, summary, facts, sections }`) and chapter 17 K59.

| File | What |
|---|---|
| `<kind>/detail.ts` | One kind: the decoder of what the page reads of the object (`<kind>Detail(record)`: each field kept only when it has the type the API gives it), `<kind>Overview(record)` (`overviewModel`: built once per record) and `<kind>Commands(record)`. The header's word is the kind's list row's (`<kind>Row(record).status`), so the page and the row never disagree. |
| `detail/overview.ts` | `KindOverview` (the header's state, the summary line without the state, the rows of the Details card, the Conditions, the labels and the annotations), `DetailValue` (text, chips, a reference to another object, an instant, a time that is still running) and the builders (`textFact`, `tagsFact`, `refFact`, `momentFact`, `runningFact`: a row that has nothing to say is never built). |
| `detail/object.ts`, `detail/text.ts`, `detail/conditions.ts`, `detail/metadata.ts` | What every kind reads and says the same way: the metadata, the owners, the conditions, a selector, a strategy and the Pod template; the mock's words (`strategyText`, `retentionText`, `describeCron`, `counted`); the Conditions table and its roles; the labels and annotations (a key that names a credential, and the last applied configuration, is masked: its value is never in the data). A workload whose `status.observedGeneration` is behind its `metadata.generation` (`statusBehind`) says `update not observed yet`, not how many Pods are up to date. |
| `detail/view.tsx`, `detail/cells.tsx` | `detailView(overview, inputs)`: the host's `DetailView` (the chip, the identity line `Kind · Namespace · Age`, the commands, the Overview's summary and sections) drawn from the kit's atoms. A reference is a link when the plugin has a page for its kind (`detailTarget` in `index.ts` says where it goes) and plain text when it has none: no link goes nowhere. |
| `detail/commands.ts` | The commands of the header as the mock lays them out for the kind, each offered with the kit's pattern for a command that cannot be used yet (a reason, written once in the identity line, and no action). | `detail/useKindObject.ts`, `detail/useKindDetailPage.ts` | The read of one object (the Pod page's `usePod`, generalised: the catalog's `name` query dimension narrows the source view to that object, beside `namespace` for a kind that lives in one) and the page's one hook: the connection, the lane (the connection, and the namespace for a kind that lives in one), and the state of the page. A refusal (`denied`) is the plugin's own sentence and has no Retry; an object that leaves the live view after the page showed it was deleted (the title `<name> was deleted` over `It no longer exists in <where>.`, the title the contract's `not-found` state gained in K2c-2), and one the page never had is not found (the host's own title, `<name> was not found`, over `<Kind> <name> doesn't exist in <where>. It may have been deleted.`), both in place, with their tab. |
| `detail/testing.ts` | Test support: the detail fixtures and the way a golden reads what `kubectl describe` says. Nothing else imports it. |

The goldens are real: `fixtures/<kind>-detail.json` is every object of a kind cluster as `kubectl get -o json` prints it, and what `kubectl describe` prints of each (`hack/kinds-capture/capture-detail.mjs`; the objects that state each optional row are `hack/kinds-capture/k2c1-kinds.yaml` and `k2c1-kinds.sh`). A kind's golden holds each Details row to the object, field for field, and the derived rows (a strategy in words, a selector, the counts) to `describe` too.

What the page does not draw yet is listed, with what each needs, in the status file of K2c-1: the tables of the template and of the kind's own parts, the related objects (they need a read the curated entry does not offer), the aside cards, and every command's action.
